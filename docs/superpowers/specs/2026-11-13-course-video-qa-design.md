# 课程录播问答：设计文档

> 状态：草稿第二版（按代码核对和 GPU 测试结果修订），待用户确认。日期：2026-11-13。
> 竞品与数据依据：`../project4find-job/reports/课程录播视频理解竞品调研.md`（下文简称"调研报告"）。

## 1. 为什么做

AgentFlow 的引擎本身扎实（CAS 状态机、阶梯重试 + DLQ、Lua 令牌桶网关、投递幂等、每步存档），但面试时很难讲清楚：一句"面向 LLM 任务的分布式编排平台"让面试官想象不出谁在用、为什么需要这些机制。

这个项目给引擎一个具体的用户和场景：**用户（就是作者本人，UW 在读）回看课程录播复习**。一门课 20 到 40 小时，找"老师在哪讲过 X"要拖进度条，期末想知道一个概念在哪几讲出现、说法有没有变，没有工具能给出可信的答案。

场景选它，是因为它能让引擎的每个机制都有一个看得见的理由：一门课拆成很多讲、每讲又分下载、转写、截帧识别、建索引几个阶段，可以并行；下载会被限流、识别会失败，要按阶段重试；重跑一遍很费时间和钱，所以要断点续跑和内容去重；多个 Worker 共享模型配额，所以要全局限流。

## 2. 卖点和定位

调研结论（详见调研报告）：跨库问答 + 可点击时间戳（Panopto AI Search、Kaltura）、agent 自主挑片段（Gemini agentic 视频模式、微软 DVD）、整套 MQ 可靠性后端（DOVideo-AI 及其 8 到 10 个克隆，Vparser 甚至也用 Kafka）都已经有人做了。

所以卖点是三件别人没做到的事，加一份证明：

1. **整门课粒度**：先选讲次再检索，跨讲次输出对齐的对比表，每格带证据。
2. **语义级核验**：不只检查"引文在原文里出现过"，还检查"这段原文支持这条结论"，不支持就拦截；核验层本身的准确率也要量出来（见第 11 节）。
3. **公开评测**：跨讲次题集，和 Gemini Notebook、整份转写塞进长上下文两条基线对比，同题配对比较并给出置信区间。

后端可靠性照样写进简历，但写法是"场景里的麻烦 → 机制 → 测出来的数字"，不是罗列机制。

面试口径：预处理步骤固定，所以故意用 workflow；问答的步数取决于问题，所以用 agent；核验是代码写死的闸门，agent 绕不过去。整个系统大约八成是 workflow，两成是 agent，最难的问题在那两成里。

## 3. 目标、范围、非目标、反目标

**目标**
- 作者自己真的拿它复习 UW 的课。
- 一门公开课上跑出完整评测报告，数字可以公开、面试官可以自己点开原视频核对。
- 股票简报不在本项目范围内（用户已定）。它在独立的 fork `../stock-brief` 里，有自己的一套中间件，和这里互不影响。

**范围分两版（用户已定：评测报告优先）**

| | 第一版：能出评测报告 | 第二版：好用、好讲 |
|---|---|---|
| 导入 | YouTube 单个视频链接、本地文件 | 播放列表、B 站、一门课混放来源 |
| 摄入 | 转写、截帧 + OCR、分段、片段索引、每讲知识点目录；按讲按阶段重试、断点续跑、持久转写缓存 | 课程知识点地图、增量更新 |
| 问答 | agent + 三层核验（转写和 OCR 证据）、跨讲次对比表、追问 | 看画面（FRAME 证据） |
| 页面 | 课程库（进度）、单讲页、问答页，能用即可 | 知识点地图页 |
| 证明 | 评测报告、摄入的故障演练 | 多负载隔离（第 7 节）及其压测 |
| 部署 | 隔离的开发环境 | 长期运行的日常实例 |
| 大模型接入 | 沿用现有客户端 | 原生 Anthropic 客户端（提示缓存、批处理、图片输入） |

第二版的内容在下文各节里标"（第二版）"。

**非目标（不做）**
- 登录、多用户、权限。单用户自用。
- 手写板书识别。
- 手机端、前端打磨。
- 分片上传、断点续传上传。文件从本地路径导入或由服务器自己下载。
- 自动生成整篇笔记、闪卡、测验题（Panopto Folio 已有，拉不开差距）。
- 按幻灯片切换分段（复杂度高，先不做；评测显示检索因分段吃亏再加）。

**反目标（做成这样就算失败，哪怕功能都能跑）**
- 号称 agent，实际是固定顺序的几次大模型调用（DOVideo-AI 的 Planner → Executor → Critic 就是这样）。
- 没有评测数字，或者数字只跑了一次，或者只报对自己有利的那部分。
- 回答里出现没有证据支持的结论却没被拦下来。
- 开发或压测时动了服务器上正在跑的 agentflow、stockbrief 等服务。

## 4. 约束

- **引擎**：在现有 agentflow 仓库里做，沿用现有栈（Java 17 语法、Spring Boot、MyBatis-Plus、Redisson、Kafka、MySQL、MongoDB、pgvector，Python/FastAPI 做 RAG）。扩展方式和股票简报一样：新任务类型 = server 端 Decomposer + worker 端 Processor；多阶段任务用现有的 `StageAdvancer`（一个阶段全部落定后建下一阶段的子任务）。第一版不改引擎核心。
- **机器**：Upton 服务器（WSL2 Ubuntu 26.04，RTX 5080 笔记本 GPU 16GB，24 核，25GB 内存，磁盘剩余约 900GB）。Docker 没有 GPU 运行时，所以用 GPU 的服务直接在宿主机上跑（Python 虚拟环境）。
- **环境隔离**：服务器上长期跑着 agentflow、stockbrief、mock-interview、finance tracker、dashboard，一律不动。开发和演练用独立克隆 `~/project/agentflow-drill` + 独立 compose 项目（参照现有 `docker/chaos.yml` 的做法），用完 `down -v --rmi local`。注意 agentflow 的 `.env` 是真实模型配置，临时环境必须显式设 mock，除非就是要测真实模型。
- **日常使用的实例（第二版）**：在 Upton 上单独起一套长期运行的部署（独立的 compose 项目名、端口、数据卷），不升级、不复用现有的 `~/project/agentflow` 实例。GPU 服务以宿主机进程长期运行，崩溃后能自动拉起。
- **大模型（用户已定用 Claude）**：
  - 用 Anthropic 的 API key（Claude Code 的订阅登录不能给程序当 API 用；`agentflow/.env` 里已有一个 key）。
  - **第一版沿用现有的 `OpenAiLlmClient`**（JDK HttpClient 直连 OpenAI 兼容接口，现在就能调 Claude，支持工具调用），不写新客户端。代价：没有提示缓存和批处理，消息内容只能是文本。
  - **第二版加原生 Anthropic 客户端**（网关里多一个 `LlmClient` 实现），用于图片输入（看画面）、提示缓存、批处理。
  - 每种用途（agent、判官、每讲目录）的型号单独可配，默认 `claude-opus-5-5`；**最终用哪个型号由评测决定**（见第 11 节）。开发期测试用引擎自带的 mock 模型，真实模型只做少量冒烟测试。
- **成本**：见第 9 节。真实模型的费用记在用户的 Anthropic 账号上。
- **版权**：B 站、YouTube 视频只供个人学习，不对外公开、不二次分发；演示和评测报告只放原视频链接加时间点、简短引用。

## 5. 产品形态

网页工作台（用户已选），沿用现有控制台的原生 JS 静态页和轮询方式：

1. **课程库**：建课程；导入视频；看每讲的处理状态（排队、下载中、转写中、识别画面中、重试中、已索引、部分完成、复用）。
2. **单讲页**：视频播放器 + 带时间戳的逐字稿（点句子跳转、全文搜索）+ 幻灯片截图和 OCR 文字（可搜）+ 本讲知识点目录（每条带时间点并过核验）。
3. **问答**：可以限定单讲或整门课提问、追问。每条结论旁边是证据标签（讲次、时间点、来源是语音还是画面文字），点一下视频跳过去，旁边显示原文；被拦截的结论单独列出并说明原因。跨讲次问题输出对齐表。
4. **课程知识点地图（第二版）**：行是知识点，列是讲次，格子是出现的时间点，标出"首次出现"，点格子跳视频。

草图在 `../project4find-job/.superpowers/brainstorm/16532-1794595377/content/`（`product-form.html`、`after-upload.html`），只表达结构，不是视觉稿。

## 6. 摄入流水线（workflow）

每讲是一个任务，用 `StageAdvancer` 的多阶段表达先后：下载 → 转写和截帧识别（并行）→ 建索引。每个阶段是一个子任务。一门课的并行度来自"多讲同时处理"和"转写与截帧识别同时进行"。

1. **下载**（链接导入时）：yt-dlp，取音频和视频（视频用于截帧和播放）。失败退避重试，多次失败进 DLQ。YouTube 拦截下载时的退路是本地文件导入。按站点限制并发属于第二版（播放列表和 B 站才需要）。
2. **转写**：faster-whisper large-v3，在 Upton 的 GPU 上跑，输出带句子时间戳的文本。**一讲一个子任务，整段音频交给批处理管线（自带静音检测切分），不再把音频切成小片分给多个 Worker。** 这是第 10 节测出来的：单卡上加 Worker 吞吐不变，Worker 内批处理快 10 倍，一小时的课约 40 秒转完，分片重试已经没有意义。同一时刻只允许一个转写在 GPU 上跑。
3. **截帧 + OCR**：按画面变化截帧（场景切换阈值 + 保底间隔），相邻帧去重，CPU 上做 OCR。一讲一个子任务，多讲之间靠多个 Worker 并行（24 核）。
4. **分段**：所有视频用同一种方式：按转写的句子边界切成约 1 到 2 分钟的段，相邻段少量重叠。OCR 文字按时间挂到对应段上，作为"画面文字原文"证据。
5. **建索引**：
   - **片段索引**：段的原文（转写 + OCR）建关键词索引和向量索引。**在 agentflow-rag 里新建一张带课程、讲次、起止时间列的表，支持按这些列过滤**；不动现有的 `documents` 表和它的向量模型（那张表整表共用一个模型，换模型会把研究 agent 的知识库一起重新向量化）。向量模型默认 bge-m3（中英文都支持，本地 GPU 跑）。**不对每段调大模型做摘要。**
   - **每讲知识点目录**：每讲调一次大模型，输出知识点列表，每条带时间点和支持它的原文引用；引用过核验第 1、2 层（见第 8 节），不通过的条目丢弃。这份目录既给 agent 选讲次用，也直接展示给用户。
   - **课程知识点地图（第二版）**：把各讲的知识点合并成课程级的表，同一概念的不同叫法需要归一。
6. **增量（第二版）**：每周新增一讲只处理新的这一讲，课程级地图增量更新。

**某个阶段彻底失败时（设计决定）**：`StageAdvancer` 是一个阶段全部落定才进下一阶段，失败进 DLQ 也算落定。下载或转写失败，这一讲标成失败，不建索引。只有截帧识别失败时，这一讲标成"部分完成"：只用转写建索引，页面上明确显示"没有画面文字"；重新导入时只补失败的阶段。**不允许像 DOVideo-AI 那样悄悄跳过。**

**可靠性要求（每条都要有对应的演练或测试）**
- **持久转写缓存（新做）**：键 = 整讲音频的内容哈希 + 模型版本，值 = 转写结果，存 MySQL 或磁盘，不过期。同一个文件重新导入，转写调用次数为 0。注意现有的 `IdempotencyGuard` 不能直接当它用：那个键是"子任务 ID + 输入"、24 小时过期，防的是同一个子任务被重复投递，继续按原用途保留。
- 断点续跑：摄入途中 kill -9 Worker，恢复后已完成的阶段不重跑（被打断的那个阶段重跑，转写最多损失几十秒）。
- 按阶段重试 + DLQ，失败在进度页可见。
- 大模型的各种用途（每讲目录、agent、核验判官）共享限流（复用网关的令牌桶）。

**已知限制**：现有关键词分词把一整串中文当成一个词，中文内容的关键词检索基本失效。英文评测课不受影响；第二版接 B 站时改成按字或二元组切分。

**Worker 数量**：转写固定 1 路（见第 10 节）；下载和截帧识别吃网络和 CPU，多开 Worker 才有用。"1 个 Worker 和 3 个 Worker 导入一门课各用多久"在这两个阶段上测。

## 7. 批量摄入和交互问答：多负载隔离（第二版）

同一个产品里有两类性质完全不同的负载：**批量摄入**（导入一门课一次几十个子任务，每个跑几十秒到几分钟，占着 Worker 线程和 GPU）和**交互问答**（用户在页面上等着，对延迟敏感）；评测运行也是批量的大模型调用。共用引擎会出四个问题，现有代码里能看到成因：

| 问题 | 成因（现有代码） | 要求 |
|---|---|---|
| 排队被堵 | 所有子任务共用 `AGENTFLOW_SUBTASK` 一个 topic | 摄入子任务和问答子任务分开 topic |
| Worker 被占满 | 同一个 `SubtaskListener`，`subtask-concurrency` 默认 4 | 摄入有自己的 Worker 池（舱壁隔离） |
| 大模型额度被抢 | 网关令牌桶共享 | 按用途分桶（摄入、问答、评测），外面再套一个总桶 |
| 长任务被误判卡死 | 超时扫描用全局的 `agentflow.timeout.stuck-seconds` | 按子任务类型设超时 |

这一节要改引擎核心，所以放在评测报告之后。第一版里先把 `stuck-seconds` 调大到转写子任务够用，并避免在导入的同时跑评测。

**验收**：导入一门课的同时连续提问，记录问答的首个回答延迟；隔离前后各测一次，数字写进 benchmarks。

## 8. 问答 agent

**结构**：基于 worker 里现有的 `AgentLoop`（ReAct，原生工具调用，每步存档到 Redis，最多 10 步）。能直接复用的是循环骨架、步数上限和存档续跑；需要改造的有三处：

- 提示词现在写死是研究 agent 的，要能按 agent 类型换。
- 收尾时的摘录核对现在按 URL 组织（`seenUrls`、`textByUrl`），要改成按"讲次 + 时间区间"组织，这就是下面核验的第 1、2 层。
- 输出上限现在是 1600 token，跨讲次对比表带多条引文会被截断（评测 v3 里踩过），要按输出类型放宽。

工具：

| 工具 | 作用 |
|---|---|
| 查课程概览 | 读每讲的知识点目录（第二版加课程知识点地图），决定查哪几讲 |
| 检索片段 | 关键词 + 向量混合检索，可限定讲次、时间范围 |
| 展开上下文 | 读某讲某个时间窗前后的原文 |
| 看画面（第二版） | 把某讲某个时间点附近的几帧截图交给 Claude（图片输入）读，用于问幻灯片、公式、代码的问题 |

工具设计参考微软 Deep Video Discovery 的"全局浏览 / 片段搜索 / 看帧"，区别是我们的范围是一整门课。工具都是只读的；转写和 OCR 文本是不可信内容，里面即使混进指令，最坏结果是答错，由核验层兜一部分。

- **输出结构**：每条结论带一组证据，证据 = {讲次, 开始时间, 结束时间, 来源, 引用原文}。来源：转写（ASR）、画面文字（OCR）；第二版加画面（FRAME）。跨讲次问题输出对齐表，每格一条证据。
- **追问**：每次提问是一个新任务，最近几轮对话作为输入带上。
- **课里没讲的问题**：应该回答"找不到"，不硬答。

**核验闸门**：agent 给出最终答案后，由代码执行，agent 绕不过去：

1. **时间合法**：证据的时间点落在该讲真实存在的片段里。
2. **引文忠实**：引用原文规范化后能在该时间窗（前后留少量余量）的转写或 OCR 里找到。
3. **结论被支持**：把所有结论和各自的证据放进一次大模型判官调用里，判断原文是否支持结论。

不通过的结论从答案里移除、单独列出原因。被移除的多于一定比例时，带着失败原因让 agent 再补一轮（只补一次）。

**画面证据（FRAME，第二版）的核验**：模型从截图里读出来的文字不能当作"原文"，否则就成了模型自己给自己作证。所以 FRAME 证据跳过第 2 层，第 3 层改为把对应的几帧图片和结论一起交给多模态判官判断；这类结论在指标里单独统计。

## 9. 成本估算

转写和向量在本地 GPU 上跑，$0。大模型按每问约 3 万输入、2 千输出 token 估算（Anthropic 官方价，2026-11-03 版本，每百万 token 输入/输出）：

| 型号 | 单价 | 每问一次 | 评测主体 S1 到 S3（720 次运行） |
|---|---|---|---|
| Opus 5.5 | $4 / $20 | 约 $0.16 | 约 $115 |
| Sonnet 5.5 | $2 / $10 | 约 $0.08 | 约 $58 |
| Haiku 5.5 | $0.10 / $0.50（单次超过 10 万 token 的部分 $0.50 / $2.50） | 约 $0.004 | 约 $3 |

- 以上是没有提示缓存、没有批处理的价格，也就是第一版的实际情况。第二版接了原生客户端后可以用提示缓存（系统提示、工具定义、课程概览每问相同）和批处理接口（判官、每讲目录、长上下文基线这类单次调用半价）。
- 每讲目录：评测课约 12 讲，约 15 到 20 万输入 token（按每小时 1 万多 token 估算），Opus 不到 $1。
- 型号选择本身是评测的一部分：先用小题集比较三个型号，再决定全量评测和日常使用用哪个。全量评测如果选 Opus，建议等原生客户端的提示缓存接上再跑。

实际数字由网关的 token 记账给出，记账结果本身也写进简历。单价以当时官方价目表为准。

## 10. 转写怎么跑：测试结果（spike，已完成）

在 Upton 上用 MIT 18.06 第 2 讲（47.7 分钟，faster-whisper large-v3，fp16）测的。脚本和原始结果在服务器的 `~/spike-asr-workers/`，是一次性的，不进仓库。

| 方案 | Worker 数 | 用时 | 速度（倍实时） | 峰值显存 |
|---|---|---|---|---|
| 60 秒一段，逐段转写 | 1 | 315 秒 | 9.1 | 5.8GB |
| 同上 | 2 | 310 秒 | 9.2 | 11.2GB |
| 同上 | 3 | 327 秒 | 8.8 | 15.8GB |
| 同上（收尾重跑，对照） | 1 | 334 秒 | 8.6 | 5.8GB |
| 5 分钟一段，段内批处理（batch 8） | 1 | 39 秒 | 72.6 | 7.3GB |
| 同上 | 2 | 43 秒 | 67.0 | 13.7GB |
| 同上 | 3 | 74 秒 | 38.9 | 15.9GB |
| **整个文件批处理（batch 16）** | **1** | **30 秒** | **95.1** | **10.0GB** |

**结论**
1. **单卡上加转写 Worker 没有收益。** 1、2、3 个 Worker 的吞吐基本不变（GPU 已经被一个 Worker 占满），显存却按 Worker 数线性涨；涨到 16GB 上限附近反而变慢（5 分钟方案 3 个 Worker 慢了近一半）。
2. **提速来自 Worker 内部的批处理**，比逐段转写快 8 到 10 倍。
3. **所以转写不分片：一讲一个子任务，整个文件批处理，同一时刻只跑一路。** 一小时的课约 40 秒转完，12 小时的评测课约 8 分钟。原先设想的"切成 60 秒片段分给多个 Worker、按片段重试"被数据否定，删掉。
4. 笔记本 GPU 连续跑半小时后，同一配置慢了约 6%（315 秒 → 334 秒），量级不大。

**其他发现**
- 第一次测试里 4 个 Worker 那组显存占满 15.9GB，跑了 25 分钟没出结果，被手动终止；没有报显存不足的错误。原因推测是 WSL 下驱动把显存换到了内存里，没有验证。
- **两种方式转出的文本不一样。** 抽前 10 分钟对比：逐段方式多出约 10% 的词（1400 对 1265），其中既有 60 秒硬切处的重复和幻觉（比如片段结尾凭空出现的 "Thank you very much. Thank you."），也有批处理的静音检测漏掉的几句短话（比如 "the multiplier is three"）。没有标准答案，不能下谁更准的结论；但幻觉文本会被当成"原文"引用，对本项目更危险，所以选批处理。**转写质量要在评测课上抽样核对**（见第 11 节）。
- faster-whisper 1.2.1 + ctranslate2 4.9.0 能在 RTX 5080（Blackwell）上跑，需要把 PyAV 锁在 16 以下（新版 PyAV 去掉了 `metadata_errors` 参数）。

## 11. 评测

**评测课（用户已定）**：Berkeley Agentic AI MOOC（2025 秋，https://rdi.berkeley.edu/agentic-ai/f25 ），约 12 讲，每讲有录像和幻灯片，整门课讲 agent。没有查到明确的 CC 授权，所以报告只放数字、简短引用和原视频链接。如果 2025 秋版录像不全，退回 2024 秋版 CS294-196（https://rdi.berkeley.edu/llm-agents/f24 ）。

**题集（50 到 80 道）**
- **跨讲次题（至少三分之一）由用户自己写**，写复习时真会问的问题。不让大模型起草：能起草跨讲次题的只有长上下文模型，而它正是被比较的基线。
- **单讲题**：大模型根据单讲转写起草，用户逐题改写措辞（避免题目贴着原文、让关键词检索白占便宜）并核对答案。
- 少量"课里没讲"的题，标准答案是"找不到"。
- 每题标注：要点式标准答案 + 答案所在的讲次和时间区间（可以多个）。
- 题集在看任何系统的结果之前冻结。

**参与对比的系统**

| 编号 | 系统 | 跑法 | 能比什么 |
|---|---|---|---|
| S1 | 完整系统（agent + 三层核验） | 全部题，3 次 | 全部指标 |
| S2 | 固定 RAG 流水线（不用 agent：检索一次 → 回答 → 核验） | 全部题，3 次 | 全部指标 |
| S3 | agent 但去掉第 3 层核验 | 全部题，3 次 | 全部指标 |
| B1 | 整份转写塞进长上下文（和 S1 同一个型号，只比方法） | 约 30 题，1 次 | 答对率、证据定位、每问成本 |
| B2 | Gemini Notebook（网页，上传音频） | 约 30 题，1 次，手动 | 只比答对率（它不输出时间戳） |

**指标**：答对率（大模型判官对照要点打分 + 人工抽查）、跨讲次题答对率、证据定位命中（引用区间和标准区间有重叠）、引文忠实率、无证据结论占比、"找不到"题的正确拒答率、每题步数分布（证明 agent 真的在按问题决定步数）、每问 token 和成本、延迟。

**核验层自己的准确率（卖点 2 的证明）**
- 人工标注约 100 对"结论 + 证据"是否支持，作为标准答案，量第 3 层判官的准确率、漏拦率、误拦率。上面的"无证据结论占比"以这份人工标注校准过的判官为准，不能只由判官自己说了算。
- 不费人工的补充测试：把已通过核验的结论换上随机片段当证据，判官应该全部拒绝，量拒绝率。

**统计**
- 同一套题上做配对比较，用 bootstrap 给出差值的置信区间。跨讲次题只有 20 多道，差几个点没有统计意义。
- 简历和报告只写置信区间分得开的结论；分不开的如实写"没有显著差别"。
- S1 到 S3 各跑 3 次，报告次与次之间的波动（调研里有论文显示同一对比重跑会变号）。

**事先写下的预期（跑之前不改）**
- 预期 1：跨讲次题上 S1 的答对率高于 S2。不成立就说明这个场景里 agent 没有必要，如实写，并把 S2 作为推荐配置。
- 预期 2：S1 的无证据结论占比低于 S3，答对率不明显下降。
- 预期 3：评测课只有约 15 到 20 万 token，B1 的答对率很可能不输 S1。这种结果下卖点是：每问成本（S1 每问只读几千到几万 token，B1 每问读整门课）、证据定位命中率、无证据结论占比。不把"比长上下文更准"当成默认结论。

**型号选择**：在约 20 道题的子集上用 Haiku、Sonnet、Opus 各跑一次 S1，比较答对率和每问成本，再决定全量评测用哪个。

**人工工作量（用户）**：写约 20 道跨讲次题，改写核对约 40 道单讲题，标注约 100 对结论与证据，抽查判官打分。估计共 4 到 6 小时。

**转写质量抽查**：在评测课上抽 2 到 3 段各 10 分钟，对照 YouTube 上的字幕（没有人工字幕就人工听），统计漏掉和多出的句子。漏得多就调静音检测的参数。

**故障演练**（沿用 `scripts/fault_matrix.py` 的风格）
- 摄入途中 kill -9 Worker：全部讲次完成，已完成的阶段不重跑。
- 导入一门课，1 个 Worker 和 3 个 Worker 各用多久（下载和截帧识别阶段）。
- 同一门课重新导入：转写调用 0 次。
- 第二版：第 7 节的隔离验收。

评测和演练脚本、结果放进仓库，结果汇总进 `docs/benchmarks.md`，简历数字全部来自这里。

## 12. 留给实现者决定的

- 摄入的子任务类型怎么划分、各阶段怎么对应到 `StageAdvancer` 的阶段。
- GPU 服务的形态：独立的 Python 服务（类似 agentflow-rag）被 Java Processor 调用，还是 Python 直接消费 Kafka。媒体文件放服务器本地磁盘的共享目录即可（单机够用，多机时再上对象存储）。
- 批处理的 batch 大小和静音检测参数、OCR 引擎（Tesseract 或 PaddleOCR）、场景切换阈值、去重阈值。
- 转写缓存放 MySQL 还是磁盘。
- 判官模型和提示词；"补一轮"的触发比例。
- 播放器：本地文件直接播，YouTube 视频嵌入原站播放器并带起始时间。
- 第二版：知识点跨讲次归一的方法；原生客户端用官方 Anthropic Java SDK 还是沿用仓库"不引 SDK、JDK HttpClient 直连"的惯例。
